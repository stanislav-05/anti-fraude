## Что будет, если система заблокирует вызов скорой помощи?

**Система не может заблокировать вызов скорой. Это гарантируют три механизма, и каждый из них проверяется тестом (`tests/test_policy.py`):**

1. **Автоблокировки нет вообще.** `AUTOBLOCK = False` в `src/policy.py`. Результат скоринга — только
   рекомендация: «пометить абоненту: возможно, мошенники» или «на ручную проверку аналитику».
   Решение о блокировке принимает человек, и это отдельное решение со своей ценой ошибки, как и сказано в ТЗ.
2. **Белый список проверяется до модели.** Экстренные номера (112, 101–104, 01–04) и доверенные
   служебные номера из `data/whitelist.txt` получают риск 0 и никогда не попадают в ответ,
   как бы ни выглядели их признаки.
3. **Звонки на экстренные номера не теряются при очистке.** Короткий номер `112` не 10-значный,
   и первая версия очистки отправляла бы такой звонок в карантин как «неверный номер B».
   Теперь он сохраняется с пометкой `info_emergency_b`.

**Почему это не формальность.** Диспетчерская скорой ведёт себя «как робот»: звонит множеству
разных людей, коротко, круглосуточно, без обратных звонков. Тест
`test_dispatch_number_with_robot_profile_is_never_in_answer` показывает: **без белого списка
такой номер получает высокий риск**, а с белым списком — 0. Обычный номер с тем же профилем
при этом остаётся в ответе.

**Если ошибка всё же случится** (номер службы не внесли в белый список), последствие — предупреждение
абоненту «возможно, мошенники», а не обрыв звонка. Исправление — одна строка в `data/whitelist.txt`
без переобучения: правила прозрачны, и сразу видно, какое из них сработало.

## Как мы контролируем ложные срабатывания

За легальные массовые источники в ТЗ положен штраф, поэтому решение настроено на точность, а не на охват.

| Механизм | Что даёт |
|---|---|
| Правила-«оправдания» с минусом | «График офиса» (−45): звонки только в будни, без ночи и выходных. **17 крупных колл-центров** (588–1835 звонков) получили риск 0 |
| Порог «высокий» = 70 | В ответ идёт только совпадение нескольких независимых признаков: одного правила недостаточно |
| Уровень «проверка» | 6 спорных номеров (4 городских разовых залпа с обычной длительностью, 2 круглосуточных) **не включены** в ответ |
| Код `777` не считается схемой | 100 номеров по одному звонку — это подмешанная ошибка формата, а не мошенничество |
| Нулевая длительность ≠ «неотвеченный» | 9% звонков всех типов имеют длительность 0: это фон, а не признак |

## «Веер»: номера одной схемы делят базу жертв

Проверка `src/graph.py` — пересечение получателей у номеров одной схемы
(`overlap_share`: 0 = списки не пересекаются):

| Схема | Номеров | Звонков разным людям (сумма) | Уникальных жертв | Пересечение |
|---|---|---|---|---|
| burst | 62 | 58 303 | 58 272 | 0,1% |
| wangiri | 38 | 20 856 | 20 142 | 3,4% |
| mass | 16 | 12 808 | 12 610 | 1,5% |
| multi_sim | 15 | 1 288 | 1 287 | 0,1% |

- Ни одна пара из 133 кандидатов не обзванивает общий список (максимальный коэффициент Жаккара 0,005).
  Каждый номер работает со своим куском базы — это и есть «веер» из ТЗ: по отдельности номер выглядит
  скромнее, вместе схема охватила **около 92 тысяч разных людей**.
- Схемы работают «сменами»: каждый день выходят 8–16 новых номеров-залпов, а 14–16 «медленных роботов»
  звонят все 5 дней.
- 5 номеров из ответа делили SIM-карту с номером, у которого низкий риск. Такие «соседи по SIM» — кандидаты
  на ручную проверку, но в ответ автоматически не включены.

## Объяснимость

У каждого номера и каждого звонка есть список сработавших правил с баллами, как в карточке из ТЗ
(`reports/call_cards.md`, `python -m src.call_risk --number <номер>`):

```
+7 025 ***-**-58 → +7 210 ***-**-22
2 окт, 16:43:57 · 11 сек · исходящий
РИСК 100
   +40  номер A: 2231 звонков за час
   +35  номер A: профиль робота: медиана 11 с
   ...
рекомендация: пометить абоненту: «возможно, мошенники» · автоблокировка: нет
```

По всем 2 352 713 звонкам: высокий риск — 94 421 (4,0%), проверка — 2 922 (0,1%),
низкий — 2 255 370 (95,9%). Автоблокировок — 0. Высокий риск почти целиком приходится на звонки
127 номеров из ответа; кроме того, отдельно отмечаются перезвоны жертв на номера wangiri.

Правила записаны в одном месте (`src/scoring.py`, `RULES`): регулятору можно показать полный список
условий и баллов, а аналитику — какое правило сработало у конкретного номера.

## ML-модели: второе мнение к правилам

Разметки нет, поэтому CatBoost учится на псевдометках от правил: 127 номеров «высокий» = 1,
56 290 активных номеров (≥ 10 исходящих) с риском < 20 = 0. Чтобы модель не просто пересказывала
правила, обучены две модели (`src/model.py`), обе проверены 5-кратной кросс-валидацией
(каждый номер оценён моделью, которая его не видела):

| Модель | Признаки | PR-AUC | Полнота | Ложные срабатывания |
|---|---|---|---|---|
| `full` | все | 1,000 | 127 из 127 | 0 из 56 290 |
| `independent` | **без** 12 признаков, на которых построены правила | 0,9999 | 126 из 127 | 2 из 56 290 |

- **Схема видна не только через пороги правил.** Модель, которой не показали ни пик звонков за час,
  ни число получателей, ни длительность, ни перезвоны, всё равно находит 126 из 127 номеров —
  по ритму звонков (паузы < 1 мин), времени активности, доле сбросов.
- **Ошибки независимой модели объяснимы и подтверждают нужность правил-оправданий.** 2 ложных
  срабатывания — маленькие колл-центры (~110 звонков, график офиса): без признака «выходные»
  модель не видит график. Единственный пропуск — номер на нескольких SIM: число SIM есть только в правилах.
- **Колл-центры:** ни один из 17 крупных колл-центров модель не отметила.
- **Второе мнение по спорным номерам.** Модель уверенно (вероятность > 0,999) относит к схеме
  6 городских номеров с одинаковым шаблоном: 300–400 звонков за 1–1,5 часа подряд (паузы < 1 мин),
  все получатели разные, медиана 25–27 с, никто не перезвонил. 4 из них правила оставили на проверке,
  2 — с низким риском (пик за час 251–262, чуть ниже порога 300). Это кандидаты на ручной разбор,
  в ответ автоматически не добавлены. Два круглосуточных номера модель фродом не считает (вероятность 0,016).
- **Isolation Forest** (без меток, 12 109 номеров с ≥ 20 исходящими) отмечает 592 аномалии:
  все 127 номеров из ответа, но и все 17 колл-центров. Это поиск «необычного», а не «мошеннического»:
  из 459 аномалий вне правил 231 — номера, которые много звонят узкому кругу (≤ 100 собеседников),
  и у 173 из них больше половины собеседников перезванивают (семья, работа). Поэтому IF используется только как источник гипотез для аналитика.

Проверка по дням (обучение на 1–3 октября, тест на 4–5, где номера-залпы новые) запускается
автоматически при наличии `calls.parquet`.

## Качество данных

2 353 333 строки → 2 352 713 чистых записей, 413 в карантине (0,02%), 207 точных дублей удалено.
Каждое исправление помечено флагом `fix_*`, каждая отброшенная строка сохранена с причиной

## Ограничения метода

- **Нет разметки.** Пороги подобраны по распределениям (у 99,9% номеров не больше 180 звонков за 5 дней)
  и по разбору профилей, а не обучены на размеченных данных. Точность на закрытом наборе заранее неизвестна.
- **Пять дней данных.** Признаки «возраст номера» и «регулярность по неделям» почти не работают.
- **Нет статуса ответа.** Отличить «не ответили» от «ответили и сразу сбросили» нельзя.
- **Спорные профили остаются спорными.** Разовый городской залп с обычной длительностью может быть
  и мошенничеством, и легальным оповещением; такие номера оставлены человеку.
- **ML учится на метках правил.** Высокие метрики кросс-валидации означают согласованность модели
  с правилами, а не точность на закрытом наборе; независимое подтверждение даёт только модель
  без признаков правил и проверка на новых номерах по дням.
- **Белый список ведётся вручную.** Номер службы, которого нет в списке, защищён только отсутствием
  автоблокировки.
